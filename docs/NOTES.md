# Notes

Real problems I ran into while doing the task, in order.

## 3 November 2026

- **Python 3.9 and the latest Playwright do not mix.** The task says Python 3.9+, but Playwright for Python dropped 3.9 in 1.61 (June 2026): `pip install playwright` on 3.9 silently installs an older version than on 3.12. I pinned `playwright==1.60.0`, the last release that supports 3.9, so every machine gets the same Playwright and the same Chromium build. CI runs the tests on 3.9, 3.12 and 3.14.
- **Looked at the reference video first.** I dumped frames of `output.webm` with Playwright itself (a `<video>` element, seek, screenshot), because there is no ffmpeg on my machine. That gave the target look: callout under the search box, white arrow, yellow circle behind it.
- **The first submit button is hidden.** The first run failed on `form button[type="submit"]`: on DuckDuckGo it matches a 0 px wide button, and the visible "Search" button appears in the suggestion box only after typing. I take the first visible match now (`>> visible=true`).
- **DuckDuckGo blocks headless Chromium.** The second run typed the query, clicked the button and then waited 30 s for nothing: the frames showed "Unexpected error. Please try again", the URL was `static-pages/home-error/418.html`. I compared in one script: headless gives the error page, a normal window gives results. So the browser runs with a window by default. I did not try to disguise the headless browser.
- **On my PC the bundled Chromium did not start with a window** ("side-by-side configuration is incorrect"). The same files started fine from another folder; only folders inside `AppData\Local` (except `Temp`) failed. This is my Windows build, not the project, so I kept the browsers in `C:\Users\USER\ms-playwright` and set `PLAYWRIGHT_BROWSERS_PATH` for my runs. CI on a clean Ubuntu installs Chromium the normal way.
- **The ripple was there, but not in the video.** Tests said the ripple element appears, and the frames showed almost nothing. Two reasons, found by cutting the frames around each click: the ripple had the same size as the yellow circle and hid behind it, and the search click starts a navigation, so the page was gone before the ripple was painted. Now the ripple is a strong orange ring that grows a bit past the circle, and Python starts it 0.3 s before the real click.
- **The cursor made a detour to the first result.** The results list was still shifting while the cursor moved, so it aimed at an old position and had to turn. Now it waits until the target stops moving, and checks after the move that it is still on it.
- **Up to 10 s of an empty white screen while the results load.** The results page stays blank until DuckDuckGo renders it, and my cursor waited for `DOMContentLoaded` to appear. Init scripts run before `<html>` exists, so I mount the cursor with a `MutationObserver` as soon as `<html>` appears. The page is still white for a moment, but the cursor stays on screen.
- **The page language followed my computer.** The first videos had the Russian DuckDuckGo interface. The CSV has a `Language` column, so it is now the browser locale; anything that is not a language code falls back to English.
- **A test was wrong, not the code.** `page.evaluate` returns the promise of `ShowCallout` and waits for it, so the test looked for the callout after it was already gone. The test now starts the callout without waiting.
- **The first result is someone else's site.** For Manchester it was designrush.com, which shows a Cloudflare "security verification" page. The click is correct, the video just ends on that page. Not something to work around.

## 6 November 2026 (Task 2)

- **requests 2.33 does not install on Python 3.9.** It needs 3.10 since 2.33.0. I pinned `requests==2.32.5`, the last release for 3.9, and `flask==3.1.3` (needs 3.9+). Checked that pip resolves all three pins for 3.9, 3.12 and 3.14 on Windows and Linux.
- **werkzeug is not on the allowed list.** Flask installs it, but the task allows only flask, requests and playwright, so I did not import `werkzeug.utils.secure_filename` in the service and wrote a small name cleaner with `re`. The tests use `werkzeug.serving.make_server` to run a real threaded server; that is test code only.
- **Two companies, one file.** `A B` and `A_B` both clean up to `A_B.webm`, so the second upload would overwrite the first company's video. The service now checks in the database who owns the name and adds a short hash if it is taken. A test agent then found the same problem with `acme` and `ACME`: on Windows file names ignore case, so `acme.webm` and `ACME.webm` are one file, while my check compared the strings exactly. Fixed with `COLLATE NOCASE`. Linux CI would never have shown it.
- **Windows cannot replace a file that is being read.** I held a download of a video open and uploaded the same company again: `os.replace` failed with `PermissionError`. The service retries 5 times (0.8 s) and then answers 503 with a clear message instead of a 500; after the download was closed the same upload worked. On Linux the replace just works.
- **A hidden-file check that could be bypassed.** The independent code review found that `/media/x/../.upload-....part` passed my "no names starting with a dot" check, because Flask normalises the path after my check. `uploads/` has no subfolders, so the route now takes a plain file name without `/`. The test failed on the old code and passes now.
- **The preview window in the README.** A page screenshot from Playwright shows only the video frame, it looks like a normal web page. For `docs/img/preview.png` I captured the real Chromium window (address bar with the `/media/...` URL and the player controls at 0:05 of 0:31).
- **The preview needs a screen.** The task says `headless=False`. CI has no screen, so the tests run under `xvfb-run`.
- **CI went red without a code change.** The first push of Task 2 failed in the install step on all three Pythons: `Playwright does not support chromium on ubuntu26.04-x64`. GitHub had moved `ubuntu-latest` to Ubuntu 26.04, and Playwright 1.60 (pinned because it is the last one for Python 3.9) does not know it. The re-run of the old Task 1 commit failed the same way. The workflow now pins `runs-on: ubuntu-24.04`.

## 9 November 2026 (Internship task 1: Docker, Apache + mod_wsgi, PostgreSQL)

- **Which mod_wsgi.** The task warns that `libapache2-mod-wsgi-py3` must match the Python of the image. In Debian bookworm that package is built for Python 3.11, while the image is `python:3.12-slim`. So mod_wsgi is built with `pip install mod-wsgi` for the image's own Python, and `mod_wsgi-express module-config` writes the `LoadModule` line. That needs a compiler and `apache2-dev`, so the Dockerfile has two stages and the final image gets only the ready venv. The first build took 6.5 minutes on my laptop, mostly compiling.
- **Versions for Python 3.9 again.** psycopg2 2.9.13 (the newest) needs Python 3.10, and `pip install psycopg2-binary` on 3.9 would quietly take an older one. I checked the wheels: 2.9.12 is the last one with wheels for 3.9 and also has them for 3.14, on Windows and Linux. Pinned 2.9.12 everywhere. mod-wsgi 6.1.1 needs 3.10+, fine inside the image (3.12).
- **pg_isready says "ready" too early.** On the very first start the postgres image creates the database with a temporary server that listens only on a Unix socket, then stops it and starts the real one. I polled `pg_isready` every 50 ms inside the container during a first start: over the socket it answered OK at 12:25:00.64 (the temporary server), then NO again, and the real server was up at 12:25:01.95; over TCP (`-h 127.0.0.1`) it said OK only for the real server. So the healthcheck uses `-h 127.0.0.1`.
- **`depends_on` is not the whole story.** Docker Desktop stopped while my laptop was asleep. After I started it again, `restart: unless-stopped` started `web` and `db` at the same moment, and `depends_on` does not apply there. The web log shows 4 attempts with `the database system is starting up`, then `database is ready after 5 attempts`. Without the retry loop in `create_app()` the app would have failed to load.
- **Advisory locks.** SQLite's `BEGIN IMMEDIATE` locked the whole file; PostgreSQL has nothing like that, and Apache runs 2 processes, so a Python lock is not enough. I used `pg_advisory_xact_lock`. To be sure it matters, I removed each lock for one run: with 8 threads creating the table at once PostgreSQL failed with `duplicate key value violates unique constraint "pg_class_relname_nsp_index"` (`CREATE TABLE IF NOT EXISTS` is not safe in parallel), and the parallel upload test failed too. With the locks both pass.
- **The app loads at start, not on the first request.** By default mod_wsgi imports the `.wsgi` file on the first request, so "wait for the database" would happen inside someone's request. With `process-group` and `application-group` on `WSGIScriptAlias` it loads when the daemon starts: in the log both processes (pid 9 and 10) wait for the database before any request.
- **Waiting looked slower than 1 s per attempt.** With `db` stopped, the attempts came every 5 s, not every 1 s: resolving the name `db` of a stopped container takes about 4 s to fail. The limit is by time (`DB_WAIT_SECONDS`, 60), so it still ends after 60 s.
- **The database never comes.** After 60 s the app logs `RuntimeError: database ... is not ready after 60 s`, Apache keeps running, the healthcheck marks `web` unhealthy. mod_wsgi tries to load the app again on the next request, so after `db` was back the next request got 200 without restarting anything.
- **Logs.** Debian's Apache writes to files in `/var/log/apache2`, and access lines of a VirtualHost go to `other_vhosts_access.log`. I pointed the logs to stdout/stderr so `docker compose logs web` shows them, and do not log the healthcheck (`curl -A healthcheck`), otherwise there is a line every 10 s. Messages of the app appear as `[wsgi:error]`: mod_wsgi marks everything from stderr that way, it is not an error.
- **The tests need a real PostgreSQL.** A mock would not show the locks or the SQL. Locally a throwaway `postgres:16` container on port 5433, in CI a GitHub Actions service. The tests drop the table, so they refuse a database whose name does not end with `_test`; in CI `REQUIRE_DB=1` makes a missing database a failure, not a quiet skip (checked: with Docker stopped all database tests failed with a clear message).
- **The live run.** `capture_video.py --server http://localhost:8000` uploaded and previewed Berlin and Stockholm; Manchester failed twice on `Page.goto: Timeout 30000ms` while opening DuckDuckGo (my network was slow, `curl` needed 5 s for the start page), before the service was involved. The third try worked.
